# Galene feature map

The feature map follows the public tenant API routes and application manifest contract in [the pinned snapshot](contracts.md). Check the snapshot before depending on a route because permissions and payloads can change.

A platform feature is not automatically granted to an app. For app-to-Core calls, declare the manifest's `core_api` capability when needed, then use the documented API with the signed-in tenant user's supported authentication context and the endpoint's permission. The capability does not mint a service token, bypass RBAC, or authorize access to another tenant. If the app has no supported way to make an authenticated tenant call, use the platform's documented agent/session flow or keep that integration out of scope. Never read tenant databases, connector secrets, or platform credentials directly.

| Area | Public entrypoint and prerequisite | App-builder path |
|---|---|---|
| Core and app access | `GET /tenant/applications/accessible` and `GET /tenant/applications/{application_slug}/access`; tenant user authentication. The latter resolves app visibility and declared action permissions. | Use these contracts for the current user's app visibility/actions. Manifest `permissions` are client-enforced action names; bind them to tenant roles during installation and enforce each action in the app. Do not treat a declared action as an API permission. |
| Models | Manifest `model_requirements` declares named LLM/embedding roles, slot, modalities, and component environment targets. Tenant model calls include `GET /v1/models` or `GET /models/catalog` (`model.list`), `POST /v1/chat/completions` (`inference.chat.create`), `POST /v1/embeddings` (`inference.embedding.create`), and `POST /v1/responses` (`response.create`). | Prefer declared model roles and publisher/tenant-selected model bindings. Core resolves the tenant's model assignment and provides its generated model context; do not request provider keys or hard-code provider endpoints. Direct model API calls still need a supported tenant auth context and the listed permission. |
| Document ingestion | Declare an app `filesystem_resources` entry. Ensure its instance with `PUT /tenant/applications/{application_slug}/resources/filesystems/{resource_name}`, then upload with `POST /tenant/applications/{application_slug}/resources/filesystems/{resource_name}/sessions/{session_id}/documents`; both require `application.resource.use` and the upload is scoped to a session owned by the current user. A successful document upload queues ingestion. Check `GET /rag/files/{attachment_id}/status` with `rag.get`. | Use the application resource flow for app-owned, session-scoped documents. For an ordinary tenant filesystem, `POST /filesystems/{filesystem_id}/documents` requires `fs.write` plus filesystem access and writability. It creates the tracked attachment and ingestion outbox. Do not call ingestion workers or task queues directly. |
| Browsing | For a configured SharePoint KB connector, `GET /connectors/kb/{kb_connector_id}/drives` and `GET /connectors/kb/{kb_connector_id}/browse?path=...` require `connector.test`. The tenant's web-search provider/scraper chain is configured through its supported control surface and consumed by the agent-side `web_search` tool. | The connector browse endpoints inspect the configured source; they are not a general-purpose browser automation API. Use web search through the documented agent/session surface when the app workflow has one. There is no generic browser capability in the application manifest; do not copy browser sessions or worker credentials. |
| Sandbox | `GET /sandbox/settings` (`sandbox.read`) reads tenant policy; `PUT /sandbox/settings` (`sandbox.update`) changes allowed tenant settings; `GET /sandbox/images` (`sandbox_image.list`) and `POST /sandbox/images` (`sandbox_image.create`) manage tenant image proposals. Image approval and platform ceilings are separate Control Plane operations. | These routes configure policy and images; they do not submit arbitrary code. For session-scoped execution, opt into the committed session-execution application contract: its manifest must name a routable backend component and declare the required sensitive assertion-key and installation-ID environment fields. Route work through the authorized Galene session/agent flow. Do not call internal executor or sandbox-service endpoints. |
| Knowledge base | Create/list connectors at `/connectors/kb` (`connector.create`, `connector.list`); create/start sync configurations at `/connectors/kb/sync-configs` and `.../{config_id}/start` (`kb_sync.create`, `kb_sync.start`). Tenant administrators configure source credentials; Core stores their secret references. Retrieve indexed content through `POST /rag/search` or `POST /v1/vector_stores/{vector_store_id}/search` with `rag.search`; both operate within tenant/filesystem authorization. | Use a tenant-configured connector and its mirrored filesystem, then query indexed content through RAG/vector-store APIs. An app does not need the source connector password. Sync administration and RAG retrieval are separate permissions and responsibilities. |
| Connectors | Database connectors are managed through `/tenant/db-connectors` with `db_connector.*` permissions (for example `db_connector.list`, `db_connector.get`, `db_connector.test_connection`, `db_connector.discover`). MCP connectors are managed through tenant MCP routes with `mcp_connector.*`; agents can bind configured connectors through `/agent/{agent_id}/mcp-connectors` using `agent.get`/`agent.update`. | Treat these as tenant configuration and agent-tool integrations, not a generic app query API. For KB, use the explicit sync-and-RAG path above. For database or MCP-backed app behavior, use an explicitly documented tenant API/agent tool with tenant authorization; never extract connector credentials or query platform/tenant tables directly. |

New manifests accept these canonical capabilities: `core_api`, `identity_provider`, `object_storage`, `queue`, and `memory_db`. Legacy values such as `direct_tenant_db`, `redis`, `temporal`, and `oidc_client` are not valid for a new release. Application-scoped PostgreSQL is declared with `database_resources`; the app runs its migrations at startup using its runtime `DATABASE_URL`.

Keep behavior aligned on Elettra/Docker Compose and Arethusa/Kubernetes. The app manifest declares product intent; platform adapters own environment-specific materialization. Record a missing tenant-facing contract as an assumption or follow-up rather than implementing a private platform integration.
