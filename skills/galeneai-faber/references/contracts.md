# App contracts and versioned snapshots

Use the contract files in [contracts/](contracts/) as the public authoring reference:

- [Application manifest JSON Schema](contracts/application-manifest.schema.json) is the public authoring snapshot for new app versions.
- [OpenAPI snapshot](contracts/application-api.openapi.yaml) records the public package, validation, registry, import, availability, tenant deployment, sign-in, application service, installed MCP/owner consent and inference HTTP routes used by this skill. WebSocket protocols are recorded separately in [inference interfaces](inference-gateway.md#realtime-protocol-and-completion).
- [Snapshot lock](contracts/snapshot-lock.json) records the exact Platform Core commit, source files, and SHA-256 hashes of both exported contract files.
- [Public external-registry manifest example](contracts/examples/team-notes-manifest.json) and [multi-component archive-import request example](contracts/examples/multi-component-archive-import-manifest.json) use only fictional IDs and digests.

The packaged contracts include manifest 1.0 service/resource requirements and `internal_endpoints`, explicit installation approvals/bindings, `/v1/services` and ordinary job-consent, notification inbox/preferences, resource selection and credential rotation routes. They also include installed MCP connector registration, catalog refresh/selection, agent tool binding, owner delegation list/preview/approval/revocation and `/v1/services/mcp/introspect`. Read [application services](application-services.md), [examples](application-services-examples.md), [jobs/notifications](application-jobs-notifications.md) and [installed application MCP](installed-application-mcp.md) for authoring and authority boundaries. Snapshot coverage supports authoring and comparison; it does not establish tenant prerequisites, deployment readiness or completed external effects.

The lock pins Platform Core develop commit `a44fd195ea92e3387b5e7a003b79b061e95501b3`, captured on 2026-10-26. This is a source baseline, not a released version. Its offline OpenAPI reports `0.0.0+dev`: Core now reads immutable image build identity from `/opt/galene/BUILD_VERSION`, not a runtime environment version override. Do not label the export Core 1.3 or infer an earliest native release. The lock records input export hashes, focused artifact hashes, export tool versions and source-file hashes from that exact Git commit, including the public live-channel and private relay/protocol sources used to document WebSockets. No platform implementation is packaged with the skill; no runtime acceptance is implied.

For the exact target's public OpenAPI URL, follow [API discovery](api-discovery.md), including Console, Control Plane and app runtime configuration. Keep its downloaded JSON separate from the pinned files below.

**App builders:** use this published snapshot as the authoring baseline and compare only the relevant operations with the target's public `/openapi.json`. A missing or changed operation is a stop condition for that slice: do not guess a request shape or edit the pinned hashes from an app checkout. Give a minimal sanitized diagnosis and ask the responsible platform operator for the supported contract/version or prerequisite. A Core checkout is not required for app development.

**Skill maintainers:** refreshing a pinned snapshot is separate maintenance work. Verify the exact Core source revision and exported contract artifacts before updating the snapshot and source-file hashes; then update the app compatibility matrix for that new baseline. Never use an unverified source or infer a new hash from a target response. The package tool rejects a compatibility record that does not match the published pinned artifacts.

## Core compatibility

Keep manifest `schema_version: "1.0"`. New apps declare `app.requires_core: ">=2.0,<3.0"`; narrow it to a later 2.x release only when a verified feature requires it, and never assume this develop pin belongs to a given release. Legacy ranges such as `">=1.2,<2.0"` or `">=1.3,<2.0"` exclude Core 2.x and say nothing about native audio/decisions/realtime: when such an app is maintained for a Core 2.x platform, propose to the user a new app version at `">=2.0,<3.0"` with its checks repeated on Core 2.x. Keep a 1.x range only for a verified legacy release the user explicitly asks for.

Core reads its own version from the stamped image identity and checks the range at catalogue sync, import, publication, installation, update and reconciliation; a catalogue version whose range excludes the running Core is shown as incompatible and cannot be imported. Unstamped development builds report `0.0.0+dev` and match no versioned range. `doctor.py` and `validate.py` warn about a missing, legacy or 1.x-admitting range; `validate.py --target-url` reads the target's public OpenAPI version and fails when the range excludes it. Core checks the complete PEP 440 constraint at preflight, publication, installation, update and reconciliation; malformed or incompatible constraints are rejected. Do not use npm caret syntax or weaken a release constraint to bypass an incompatible target.

The packaged schema and focused OpenAPI were exported offline without running Core's lifespan, migrations, provider calls or stack. OpenAPI `info.version` retains the honest development identity; `x-platform-core-commit` and the lock identify the source revision. The excerpt includes the previous application routes plus public inference HTTP routes and the complete closure of referenced schemas; path/schema counts are in the lock. WebSocket routes are not fabricated as HTTP operations. Older Core revisions may ignore unknown fields and may not enforce `requires_core`. A successful install or a written version range on those revisions cannot establish support.

For nonempty `service_requirements`, `resource_requirements`, `internal_endpoints` or `model_requirements`, Faber checks the exact target's public OpenAPI before installation or direct publication preflight. Qualified version families are stable Core 1.x at least 1.3.0 and stable 2.x, still requiring the manifest/approval/binding fields and service HTTP routes. This is structural compatibility, not blanket certification of a major version. Unknown, unstamped development, prerelease and future-major identities remain closed. The check additionally requires declared inference operations, model slots/capabilities/modalities and requested context-minimum support; `speak` requires its typed public application channel. Native enablement, model readiness and WebSocket protocols are separate [inference prerequisites](inference-gateway.md). Internal endpoints also require the closed endpoint contract and MCP introspection where declared. The public check sends no bearer and cannot replace Core's full PEP 440 validation, grants or tenant prerequisites. Manifests with all four declarations absent/empty retain their legacy flow.

The schema is for authoring and offline checks. It cannot express every Pydantic cross-field rule, prove that a registry source exists and is usable, or authorize a tenant action. Before creating a package or publishing a direct version, call `POST /controlplane/application-manifests/validate` with `{package_slug, version, manifest}` using `controlplane.applications.manage`. A valid manifest returns `200 {valid: true, errors: []}`; an invalid one returns `422 {valid: false, errors: [{path, message, type}]}`. Paths include array indices. The read-only response never echoes the manifest or validation context. Core repeats validation when creating the immutable version, so the validator is a preflight, not a replacement for publication.

This packaged OpenAPI includes application publication, registry, availability, deployment, public tenant sign-in and direct application service/management contracts. Generic app SSO return registration and manifest `authentication.login_path` are absent from this baseline; its public SSO facade registers only Assistant at `/login`. Public password-reset routes are also absent; optional recovery templates require separate target verification as described in [tenant authentication](tenant-authentication.md#password-recovery-requires-a-separate-target-contract). Further runtime integration is covered by [tenant authentication](tenant-authentication.md); fetch `/openapi.json` from the exact target Core version and fail closed if its operation or schema differs from the pinned baseline. Do not infer runtime tenant request bodies from the manifest schema.

A direct new version must not contain legacy capability names such as `direct_tenant_db`, `redis`, `temporal`, or `oidc_client`, or `connectivity.outbound_hosts`. Old immutable manifests may be normalized for compatibility, but new publication rejects these values. `archive_import` targets are accepted only by the dedicated archive-import flow; the direct version validator and version-creation route reject them.

For publisher installation, use the documented Control Plane tenant catalog and application deployment endpoints with the required publisher permissions. Select the tenant explicitly from that catalog and verify the app deployment in that tenant. A publisher-authorized Control Plane flow is the supported delegated installation path, not a tenant-authorization bypass. If the user chooses tenant-scoped installation instead, use that tenant's available application catalog and tenant deployment API with a tenant-scoped token. In either flow, report the selected tenant slug with the returned deployment ID/status.
