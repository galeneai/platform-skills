# Next.js and Python tenant sign-in examples

Use these examples when implementing app-owned login; SSO return handling is conditional on a supported public return contract for the selected app. Read [tenant authentication](tenant-authentication.md) and [API discovery](api-discovery.md) first. Copy/adapt the files to the app; they are integration examples, not a new authentication authority or a complete project.

- [Next.js login page](../assets/auth/next/page.tsx): credentials, challenge-driven TOTP and temporary-password first sign-in, configured SSO choices, SSO return exchange, and in-app password reset completion.
- [Python BFF router](../assets/auth/python/tenant_auth.py): public config/credential/SSO/reset/temporary-password calls, server-owned browser binding and return URI, same-origin POST protection, token handoff to the app's existing protected session store and sanitized errors.

The selected Core baseline does not publish the password-reset routes or recovery config fields. The templates default missing reset flags to false, so ordinary login/SSO/temporary-password flows remain usable and reset requests stay disabled. Their optional reset implementation is outside this pinned contract: enable it only after separately verifying both public reset routes and the target configuration, as described in [password recovery](tenant-authentication.md#password-recovery-requires-a-separate-target-contract).

Mount the Python router at `/auth`, with the app's reverse proxy serving it on the same origin as Next.js. Copy the page to `app/login/page.tsx`. Use `fastapi` and `httpx` from the app's dependencies. Configure the resolved Core API base, explicit tenant slug, app HTTPS origin and a target-supported fixed login return path on the server. The current baseline has no manifest `authentication.login_path`. Configure an operator-confirmed tenant Console `/login` fallback only for targets that lack or disable the public reset contract. Do not let the browser supply an API base, tenant, return URI or recovery URL. Disable request-body logging, tracing capture and error-body echo on all auth routes.

The router deliberately requires two app adapters:

- `PendingStore`: expiring server-side storage with an atomic `take` operation. Store SSO browser binding and transaction ID for at most five minutes, under a random opaque cookie ID. A shared store is required for multiple BFF workers. Keep this material out of logs and browser storage.
- `establish_session(request, response, tokens)`: validate the **target-supported** token/user response and rotate/create the app session in its existing protected store. It is used after credential, SSO and temporary-password completion. Retain access/refresh values server-side; set the app's Secure, HttpOnly cookie and expose no tokens in JSON. Apply the app access checks before allowing protected workflows. Implement refresh/revocation/logout as described in tenant authentication. This hook must be implemented before the example is usable; no insecure in-memory session fallback is supplied.

The SSO example uses the public facade only when the target permits returns for the selected app. The pinned baseline permits Assistant at `/login`, so generic app SSO requires a separately verified target contract before using this branch:

1. GET tenant auth config; render enabled connectors by `display_order`, using `alias` and `display_name`. Respect `credential_login_enabled`, including SSO-only tenants. LDAP directory connectors are not browser sign-in buttons.
2. BFF generates a browser-bound secret, calls `POST .../auth/sso/start` with `alias`, fixed registered `redirect_uri` and `browser_binding`, and stores the transaction. Redirect the browser to the returned `authorization_url`. Core owns the IdP callback, state, nonce, PKCE and validation for this facade.
3. Core returns to the app's `/login?sso_transaction=<id>.<exchange-code>`. The page removes that value from the visible URL and sends it to the BFF. The BFF atomically consumes the pending transaction for this browser and checks the ID before calling `POST .../auth/sso/exchange` with that complete value and the same binding. Successful exchange creates the app session. Never exchange an IdP code directly in this facade.
4. Treat `refresh_token`, including an opaque `sso.` handle, as opaque. Use the matching public tenant `auth/refresh` and `auth/logout` routes; do not send the handle to Keycloak. The target may omit `expires_in` for SSO.

**Target prerequisite:** verify the public return contract and install the app before enabling SSO or optional reset branches. In the pinned baseline, only Assistant frontend returns at `/login` are registered; installing a generic app does not register its SSO return. If another verified target supports `authentication.login_path`, declare only what that target documents and configure the same exact return path in the BFF. The template fixes its registered return URI and never takes it from the browser.

For a separately verified reset-capable target, the BFF exposes `password_reset_enabled` and `password_reset_completion_modes`. When `application` is advertised, it requests application completion; when modes are absent on a legacy target, it omits the unsupported field and keeps Keycloak completion. The page removes `#password_reset_token` from browser history immediately, retains it only in component memory, and submits it with matching new-password fields to the BFF. Completion uses the fixed return URI, returns `completed: true`, and deliberately does not call `establish_session`. Existing callback links remain completable even if a later config read disables new reset requests. Use the Console fallback only when reset is unavailable. Do not use temporary-password challenge/complete as forgotten-password recovery.

On a typed `password_update_required` login response, the page keeps the username and temporary password in memory while asking for a confirmed new password. Its BFF endpoint calls Core's temporary-password challenge and completion in one same-origin request, so the Core challenge token is never exposed to the browser. If the challenge operation explicitly returns `totp_required`, the page adds the TOTP field and repeats the proof; it never infers that state from another 401. Successful completion passes the normal tenant tokens to `establish_session`. If completion returns `password_updated: true`, the example preserves an explicit `totp_required`, normalizes other marked challenges to `sign_in_required`, overwrites the temporary credential in memory with the new password, and moves to ordinary login. It never replays the consumed Core challenge.

Run the fixture BFF checks with `python3 -m unittest discover -s skills/galeneai-faber/assets/auth/python -v` from this repository root, using an environment with FastAPI/httpx. Run the discovery/tooling checks with the normal repository suite. Type-check the Next.js page in the app's React/TypeScript environment.

Acceptance: credentials-only initial attempt; generic 401 has no OTP or first-sign-in step; documented TOTP and password-update challenges do; temporary-password proof/completion creates a normal BFF session and rejects an expired or cross-tenant challenge; multiple/disabled/SSO-only connector states; successful SSO plus rejected replay/wrong browser/expired state; reset flag false; application reset request and completion use the fixed installed return, remove the fragment, show neutral request acceptance and require normal sign-in after completion; expired/replayed/wrong-tenant/wrong-app reset tokens share the safe 401 path; legacy targets receive no unsupported completion mode; unavailable config cannot silently enable credentials. Run the app's tests for session rotation, CSRF, tenant and app access. The skill's offline checks verify wiring and examples, not a real IdP login or email delivery.
