# Security and release

## Tenant boundary and capabilities

- Derive authority from the authenticated tenant context. Never accept a tenant id from app input as proof of authority.
- For tenant-user sign-in and calls to Core, follow [tenant authentication](tenant-authentication.md): use a user-delegated bearer in a BFF session, never invent a service account, and keep refresh tokens server-side.
- Request only manifest capabilities needed by the approved workflow. Capability approval is separate from tenant RBAC. Bind the reserved deployment access permission and each app action to tenant roles; enforce action checks in the app backend.
- Do not add unsupported fields such as historical connectivity.outbound_hosts or request direct tenant database access. Keep platform service credentials, host networking, and privileged execution out of an app release.
- Treat uploaded files, browser content, connector output, and model output as untrusted data. Validate before parsing or rendering, and keep tenant records scoped to their deployment.
- Secrets are set through the tenant's supported secret flow. Mark secret environment declarations sensitive, omit defaults, and keep plaintext out of manifests, archives, logs, test fixtures, and command arguments.
- Treat session-cookie values, including UUID-shaped values, as credentials. Do not copy them into project notes or diagnostics, or expose them in browser logs, screenshots, or exported artifacts.

## Application service authority

Read [application services](application-services.md) before declaring service/resource requirements. Core-managed component credentials authorize only explicitly approved roles/operations/bindings. Keep bootstrap and short access tokens out of the frontend and use the managed token exchange. User-mode calls additionally carry the real tenant user bearer in the documented delegation header; never manufacture a user/session or borrow personal connector tokens. Scheduled user work requires explicit offline consent with bounded scope and lifetime. Notification recipients are approved tenant-user bindings, not app-supplied addresses. MCP invocation is limited to exact approved tools and trusted schema pins. Revocation must deny subsequent work and must not trigger a hidden privilege fallback.

## App-owned database

Declare an application database resource only when needed. Core provisions an app-scoped database and injects its URL at the manifest-selected environment name, normally DATABASE_URL. Run the app's idempotent database migration command during app startup using that runtime DATABASE_URL. Keep migration source and migration history inside the app repository/image.

Do not request a Core callback, startup hook, platform-side migration command, or shared tenant database. A migration must not reach another app's schema or deployment. Make startup fail clearly when a required migration cannot complete; preserve the previous app revision and data on failed upgrades.

## Registry and image integrity

- Ask and record whether images belong in an owner-managed external OCI registry or Galene's integrated registry.
- Prefer a verified external registry source already configured in Core. If a source must be created or rotated, use `controlplane.registry_sources.manage` and enter the user's explicit credentials through the approved secure flow; verify the source before publication. The pinned `controlplane_app_publisher` role includes registry-source management, but an installation may assign a different role. External source endpoints are HTTPS origins without a path.
- The registry API accepts username/password as a pair for external source verification. The platform stores secrets server-side and returns only safe configured/verification state. Never put those values in project context, the manifest, release bundle, terminal arguments, or logs.
- Internal registry credentials are generated by the platform. Never invent, request, or embed them in an app.
- Pin released images to immutable sha256 digests. Tags may be useful during development, but release metadata must resolve and record the selected digest.
- Do not claim multi-component atomic publication to the integrated registry until its final API is present in the pinned Core snapshot.

## Runtime and document dependencies

Pin app runtime and parser dependencies to known working versions in the app's lockfile. Exercise selected parsers with representative source documents and generated exports, and review their published license and redistribution conditions before packaging them. Successful installation or an internal demo is not evidence of redistribution rights; do not claim legal approval from a license identifier alone.

## Versioning and compatibility

Use SemVer for app releases: MAJOR for incompatible app configuration/data/API changes, MINOR for backward-compatible features, PATCH for compatible fixes. Use prerelease labels for candidates. Once a version is published, keep its manifest, release notes, and image digests immutable; publish a new version for changes.

Version this skill separately with the SemVer value in SKILL.md metadata. PATCH fixes instructions without changing their workflow, MINOR adds a backward-compatible workflow or reference, and MAJOR changes required behavior or an assumed contract. A skill version is independent of each app's SemVer and the Platform Core commit recorded by the contract lock.

Maintain a small compatibility matrix alongside the app project:

| App version | Manifest schema | Platform Core baseline | Registry mode | Runtime adapters | Verification |
|---|---|---|---|---|---|
| For example, 1.2.0 | 1.0 | Exact committed Core SHA and contract snapshot hash | external-owner or integrated | Compose and Kubernetes | targeted result for each claimed adapter |

Also record any required Core range from the app manifest. An API or schema snapshot change needs a new matrix entry and compatibility check; do not silently edit a released app to match a newer contract.

## Operational logging

Before release, check that every component writes [the platform log format](logging.md) to stdout/stderr with `LOG_FORMAT=json` by default: one JSON object per line, including the startup banner and access logs, with no log files. Logs carry ids, statuses, and durations, never credentials, cookies, tokens, prompts, model output, or document content. Include the correlation and trace ids returned by Core in sanitized diagnoses.

## Delivery and installation

Keep the app portable across Compose and Kubernetes. Test the same behavior and manifest on each adapter when both are in scope; label a one-adapter result as partial. The package script emits release metadata and a manifest, not a platform-native installer or runtime image.

Install only to the tenant selected in the approved blueprint. For a publisher flow, use documented Control Plane application endpoints with the publisher permissions and bind only domains offered for that tenant by the application-domain options API. For tenant-scoped installation, use the tenant UI/API and a tenant-scoped token. Read tokens from the approved secret manager/environment; never place them in CLI flags or source files. After installation, verify the tenant-visible deployment status, configured app route, and primary workflow through authorized app interfaces.
